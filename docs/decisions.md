# 설계 결정

각 항목은 **무엇을 정했는지**와 **왜 그렇게 정했는지**를 함께 적는다.
나중에 "이거 왜 이렇게 했지?"로 헤매지 않기 위한 문서다.

---

## D-001. 재고를 옵션·수량 확정 시점에 확보한다

**결정:** B1 구매하기 → **B2 옵션·수량 확정 직후** 재고를 홀드한다. 결제 승인 후가 아니다.

```
B1 구매하기 → B2 옵션·수량 확정  ←★ 홀드
           → B4 배송지 → B5 결제 화면(타이머) → 결제하기 → point3
```

**배송지 입력보다 앞이다.** 우편번호 검색하고 상세주소까지 친 다음 품절을 통보받는 것은
아래 B안(승인 직전 확보)의 약한 버전일 뿐이고, 이 결정이 피하려는 바로 그 상황이다.

**B1 클릭 그 순간이 아닌 이유:** 옵션이 확정되기 전에는 잡을 수량을 알 수 없고,
옵션 바텀시트 이탈이 적지 않다. 두 시점의 실익 차이는 몇 초뿐이다.

**대안과 비교**

| | A. 옵션·수량 확정 시 확보 | B. 승인 직전 확보 |
|---|---|---|
| 초과 판매 | 방어됨 | 방어됨 |
| 사용자 경험 | 품절을 즉시 안다 | **인증·PIN 다 입력한 뒤 품절 통보** |
| 재고 낭비 | 이탈자가 물고 있음 | 없음 |
| 승인 실패 롤백 | 불필요 | **까다로움 (미확정 상태 관리 필요)** |

**이유:** B는 결제 확정(`committed`) 직후에 거절하게 되어 사용자가 "돈 나간 거 아니냐"고 의심한다.
그리고 승인 후에 재고 부족을 발견하면 취소 API의 시간 제약(EOB 차단, 정산 완료)과 싸워야 한다.
A의 유일한 약점인 유령 점유는 15분 만료로 대부분 해소된다.

## D-002. 홀드를 사용자에게 타이머로 노출한다

**결정:** 주문서 상단에 남은 시간을 표시. 만료 시각 15분 고정.

**이유:** 홀드를 숨기면 "왜 누구는 보호받고 누구는 아닌가"를 설명할 수 없다.
타이머가 보이면 규칙이 명시적이 되고, 만료 화면도 납득 가능해진다.

**따라서:** 실패 지점별 특별 처리(예: 세션 생성 실패 시 3분으로 단축)를 만들지 않는다.
규칙이 하나면 설명도 하나고 버그도 적다.

## D-003. 3~4번 실패는 자동 재시도로 흡수한다

**결정:** 데드락 · 락 타임아웃은 `@Retryable` 2~3회. `OutOfStockException`은 재시도하지 않는다.

**이유:** 내부 경합은 재시도로 해결되지만 외부 장애(세션 생성 실패)는 재시도해도 안 된다.
성질이 다르므로 다르게 다룬다. 재시도로 실패 자체를 줄이면 형평성 문제도 대부분 사라진다.

---

## D-004. 승인 API 호출 전에 `CAPTURE_PENDING`을 커밋한다

**결정:** 18번을 별도 트랜잭션으로 분리하고, 승인 요청 전에 커밋한다.

**이유:** 요청 컨텍스트는 메모리에만 있어서 서버가 죽으면 사라진다.
DB에 "승인을 시도했다"는 흔적이 없으면 어느 결제가 진행 중이었는지 알 방법이 없다.

**이것이 Outbox가 아닌 이유:** Outbox는 확정된 사실을 밖으로 알리는 장치다.
결과를 모르는 상태는 이벤트로 만들 수 없다. 방향이 반대다.

| | Outbox | `CAPTURE_PENDING` |
|---|---|---|
| 방향 | 내가 밖으로 알림 (write) | 밖의 상태를 확인 (read) |
| 전제 | 결과를 안다 | 결과를 모른다 |
| 상대 | 알림톡 · 메시지 브로커 | point3 |

## D-005. 승인 대사 배치가 가장 중요한 배치다

**결정:** 30초 주기로 `CAPTURE_PENDING`을 훑어 point3에 조회하고 확정한다.

**우선순위 근거**

| 빠졌을 때 | 결과 |
|---|---|
| Outbox | 알림이 안 감. 나중에 수동 발송 가능 |
| 홀드 만료 배치 | 재고가 묶임. 수동으로 풀 수 있음 |
| **대사 배치** | **결제 확정을 놓침. 다음 날 00:00 지나면 복구 불가** |

**시한이 있다.** 승인 마감이 커밋된 날의 다음 날 00:00 (KST)이라 그 전에 확정해야 한다.

## D-006. 4xx와 5xx를 분리해서 잡는다

**결정:**

```java
catch (HttpClientErrorException e)                          -> fail()     // 4xx
catch (HttpServerErrorException | ResourceAccessException e) -> pending()  // 5xx·타임아웃
```

**이유:** 4xx는 요청이 거부된 것이라 승인됐을 리 없다. 5xx와 타임아웃은 승인됐을 수 있다.
`RestClientException` 하나로 잡으면 5xx까지 실패 처리되어 미수금이 생긴다.

## D-007. 서버는 하나. MSA로 쪼개지 않는다

**결정:** 모놀리식 Spring Boot 하나. 패키지만 도메인별로 분리.

**이유:** 주문 · 재고 · 결제가 같은 트랜잭션에 묶여야 한다.
쪼개면 분산 트랜잭션과 Saga가 필요해지고, 이미 복잡한 결제 흐름에 얹으면 완성이 어렵다.
포트폴리오에서 불필요한 MSA는 오히려 "판단을 못 한 것"으로 읽힌다.

**배치 중복 실행:** 단일 인스턴스면 `@Scheduled`로 충분. 다중 인스턴스면 `FOR UPDATE SKIP LOCKED`.

## D-008. 대기열과 Redis 카운터는 넣지 않는다

**결정:** 조건부 UPDATE + 자동 재시도로 충분하다고 판단.

**이유:** 셀러가 링크를 뿌려 지인·팔로워가 사는 구조라 트래픽이 완만하다.
티켓팅처럼 오픈 시각에 집중되지 않는다. 초당 수십~수백 건은 현재 구조로 처리된다.

**확장 지점만 남긴다:** 재고 확보를 `StockGuard` 인터페이스 뒤에 두어
나중에 `QueuedStockGuard`나 Redis 구현으로 교체할 수 있게 한다.

**단계적 확장 순서:** 조건부 UPDATE → 마감 폼 캐시 차단 → Redis 카운터 → 대기열

## D-009. 주문을 `order_group` / `orders` 두 계층으로 나눈다

**결정:**

```
order_group  ← 결제 1회 · 배송지 1개 · 배송비 1회
   └ orders  ← 판매 폼별. 상태 머신이 여기서 돈다
        └ order_item
```

**이유:** 장바구니로 여러 판매 폼을 묶어 사면 배송비를 한 번만 내야 하므로 결제창도 한 번이어야 한다.
그런데 진행 상태는 폼마다 다르다(A는 마감, B는 아직 모집중). 하나의 `status`로 표현할 수 없다.

**따라서** `payment`와 `shipping`은 `order_group`에, 재고 홀드는 `orders`에 붙는다.

## D-010. 주문 시점 값을 스냅샷으로 복사한다

**결정:** `order_item`에 `unit_price`, `extra_price`, `product_name`, `option_name`을 복사 저장.

**이유:** 셀러가 나중에 가격을 바꾸거나 옵션을 삭제해도 과거 주문 내역은 그대로여야 한다.
`product`를 조인해서 표시하면 옵션이 삭제된 순간 주문 내역이 깨진다.

---

## D-011. 취소는 세션 단위로 호출한다

**결정:** 사용자는 "주문을 취소"하고, 서버가 이를 1~2건의 결제 취소로 번역한다.

**주의사항**

- 세금 3종을 **직접 계산**해서 넣는다. point3가 자동 계산하지 않는다
- `Idempotency-Key`는 **중복 차단용이지 재시도용이 아니다.** 같은 키 재전송 시 409
- 결과가 불확실하면 재요청하지 말고 상태 조회 먼저
- EOB 차단 시간대(23:30~00:30 KST)에는 취소 불가 → 버튼 비활성화 + 안내

**따라서** `payment`에 `supply_amount`, `vat`, `tax_free_amount`를 결제 시점에 저장해 둔다.

## D-012. Outbox는 알림톡 발송용으로만 쓴다

**결정:** 결제 확정 트랜잭션에서 이벤트를 적재하고, 릴레이가 알림톡을 발송한다.

**이유:** 2차금 청구 알림이 유실되면 구매자가 결제할 줄 모른다. 알림이 곧 결제 요청이라 유실 비용이 크다.
대량 발송이라 어디까지 보냈는지 추적할 수단도 필요하다.

**우선순위는 낮다.** 대사 배치와 홀드 만료 배치를 먼저 완성한다.
그때까지는 `@TransactionalEventListener(AFTER_COMMIT)`로 두고 나중에 교체해도 된다.

---

## D-013. SDK 방식을 기본으로 쓴다

**결정:** point3 JavaScript SDK. iframe 직접 연동은 하지 않는다.

**이유:** SDK는 iframe 생성 · 전환 · 정리를 대신 해주고, `postMessage` 4단계 검증 부담이 없다.
`successUrl` 리다이렉트로 인한 페이지 리로드가 유일한 단점인데,
같은 경로로 돌아오게 하면 체감이 거의 없다.

**iframe이 필요해지는 조건:** 결제창 브랜드 컬러, 결제창 크기·위치 제어, 외부 스크립트 반입 불가 환경.
해당 사항이 생기면 그때 전환한다. **서버 코드는 두 방식이 동일하므로 프론트만 바꾸면 된다.**

## D-014. 상태 조회 API는 부작용이 없어야 한다

**결정:** `GET /api/orders/{groupNo}/status`는 읽기 전용.

**이유:** 프론트는 승인 요청이 실패하면 **승인을 재요청하지 않고 조회만 반복**한다.
조회에서 승인을 시도하면 폴링할 때마다 결제가 시도된다.

**프론트 원칙:** 실패 화면은 서버가 `failed`라고 명시했을 때만.
네트워크 에러 · 타임아웃 · 500은 전부 "확인 중"으로 수렴한다.

## D-015. 비회원은 재고를 홀드하지 않는다

**결정:** 비로그인 상태에서 구매하기·장바구니 담기를 누르면 **홀드 없이** 카카오 로그인으로 보낸다.
재고는 로그인이 끝난 뒤 `POST /checkout-sessions` 에서 처음 잡는다.

```
비로그인
  B1 구매하기 → B2 옵션·수량 확정
       ↓  (아직 홀드 없음)
  GET /auth/kakao/login?returnTo=/products/12?optionId=100&qty=1
       ↓
  카카오 동의 → 콜백 → 세션 발급 → returnTo 로 302
       ↓
  복귀 → 프론트가 쿼리로 선택 복원 → POST /checkout-sessions 자동 호출  ←★ 여기서 홀드
```

**이유 1 — 익명 홀드는 재고 잠금 공격이 된다.**
신원 없이 홀드가 되면 세션만 갈아가며 재고를 15분씩 전부 잠글 수 있다.
선착순 공동구매에서 치명적이다. 카카오 로그인은 우리가 가진 유일한 신원 확인 수단이자
재고를 잠그는 데 드는 최소 비용이다.

**이유 2 — 스키마가 buyer 를 요구한다.**
`stock_hold → orders → order_group.buyer_id (NOT NULL)`, `cart.buyer_id (NOT NULL)`.
익명 홀드를 하려면 이 체인 전체를 nullable 로 풀거나 게스트 buyer 행을 만들어야 한다.

**넘기는 것은 재고가 아니라 의도다.**
`returnTo` 쿠키(httpOnly · 상대경로 검증)에 옵션·수량을 실어 보내고,
복귀 후 프론트가 선택을 복원해 홀드를 **자동으로** 재시도한다.
사용자가 구매하기를 다시 눌러야 하면 그만큼 시간이 더 흐른다.

**받아들이는 비용:** 로그인 왕복 중 품절될 수 있다. 막을 방법이 없다. 대신 줄인다.

- 이미 카카오에 로그인돼 있으면 동의 화면 없이 수백 ms 만에 복귀한다 (대부분의 경우)
- B1 에서 `/availability` 로 재고 0 이면 구매하기를 비활성화해 왕복 자체를 막는다
- 복귀 후 자동 호출이 중복되면 `ACTIVE_SESSION_EXISTS` 로 기존 홀드를 이어받는다

**장바구니도 같다.** 담기를 누르면 로그인으로 보내고, 복귀 후 자동으로 담는다.

## D-016. 운영은 EC2 한 대에 Docker Compose 로 올린다

**결정:** ECS Fargate 대신 **t3.small 단일 인스턴스**에 앱·MySQL·Caddy 를 컨테이너로 띄운다.
관리형 DB(RDS)도 쓰지 않는다. 배포는 GitHub Actions → ECR → SSM 으로 자동화한다.

**대안과 비교**

| | A. EC2 단일 | B. ECS Fargate + RDS |
|---|---|---|
| 월 비용 | **$26** | $124 |
| 고정 아웃바운드 IP | EIP 로 공짜 | NAT Gateway $43/월 필요 |
| 무중단 배포 | 안 됨 (수 초 끊김) | 롤링 배포 |
| DB 백업 | EBS 스냅샷 수동 구성 | 자동 백업 · PITR |
| 서버 관리 | 필요 | 없음 |

**이유는 두 가지다.**

첫째, **비용이다.** AWS 크레딧 $100 안에서 돌려야 하는데 B 안은 3주면 소진된다.
A 안은 4~5개월 버틴다. 데모용 URL 은 살아 있어야 의미가 있다.

둘째, **point3 가 운영 서버 IP 등록을 요구한다** (`point3-api.md` 9절).
Fargate 태스크는 IP 가 매번 바뀌어서 고정 IP 로 나가려면 NAT Gateway 를 세워야 하는데,
그 NAT 하나가 앱 서버 전체보다 비싸다. EC2 는 EIP 를 붙이면 끝난다.
**요구사항 하나가 아키텍처 선택을 뒤집은 자리다.**

**약점과 대응**

| 약점 | 대응 |
|---|---|
| DB 자동 백업 없음 | EBS 스냅샷 하루 1회 · 7일 보관 (Lifecycle Manager) |
| 배포 중 단절 | `server.shutdown: graceful` 로 처리 중 요청은 마무리 |
| 앱·DB 가 메모리를 공유 | JVM `MaxRAMPercentage=50`, MySQL 버퍼풀 384M, 스왑 2GB |
| 인스턴스 장애 = 전면 장애 | 감수한다. 트래픽 규모가 이중화를 정당화하지 않는다 |

**따라서:** RDS 로 옮길 때 코드는 건드리지 않는다. prod 프로파일이 `DB_URL` 을
환경변수로 받으므로 Parameter Store 값만 바꾸면 된다.

## D-017. 배포 시크릿은 Parameter Store 에만 둔다

**결정:** 이미지에도 저장소에도 시크릿을 넣지 않는다. 배포할 때마다 EC2 가
`/moeum/prod/*` 를 읽어 `.env` 를 새로 만든다.

**이유:** 이미지에 넣으면 시크릿을 바꿀 때마다 재빌드해야 하고, ECR 을 읽을 수 있는
누구나 값을 꺼낼 수 있다. 저장소에 넣는 건 논외다.

**부수 효과:** 키 교체가 재배포 한 번으로 끝난다. 이미지는 그대로다.

**GitHub 에도 AWS 액세스 키를 두지 않는다.** OIDC 로 역할을 빌리고,
신뢰 정책의 `sub` 조건이 이 저장소 main 브랜치로 범위를 좁힌다.
포크에서 워크플로를 돌려도 역할을 못 가져간다.

## D-018. API 도메인을 프론트와 같은 등록 도메인 아래 둔다

**결정:** API 를 `shop1.cloud` 가 아니라 **`api.moeum.store`** 로 서비스한다.
프론트는 `www.moeum.store`(Vercel) 다.

**이유:** 세션 쿠키가 `SameSite=Lax` 다. 브라우저는 등록 도메인(eTLD+1) 단위로
같은 사이트인지 판단하는데, `moeum.store` 와 `shop1.cloud` 는 소유자가 같아도 남남이다.
cross-site 로 판정되면 **쿠키를 저장하지도 전송하지도 않는다.** CORS 로는 못 고친다.

`api.moeum.store` 와 `www.moeum.store` 는 등록 도메인이 같아 same-site 다.
쿠키가 그대로 동작한다. 출처(origin)는 여전히 다르므로 CORS 설정은 필요하다.
**same-site 와 same-origin 은 다른 개념이다.**

**대안과 비교**

| | A. `api.moeum.store` | B. `shop1.cloud` + `SameSite=None` |
|---|---|---|
| 코드 수정 | 없음 | 쿠키 정책 변경 |
| Chrome | 동작 | 동작 (정책 강화 중) |
| Safari · Firefox | 동작 | **서드파티 쿠키 차단으로 로그인 불가** |
| CSRF 방어 | Lax + Origin 검증 2중 | Origin 검증 단일 |
| 비용 | 0 (서브도메인) | 이미 보유 |

B 는 사파리 사용자가 로그인을 못 한다. 결제 서비스에서 받아들일 수 없다.
그리고 `SameSite=Lax` 자체가 CSRF 방어의 한 겹인데 그걸 걷어내게 된다.

**따라서:** `shop1.cloud` 는 `LEGACY_DOMAIN` 으로 함께 서빙해 인증서는 유지하되,
프론트 연동의 기준 주소는 `api.moeum.store` 하나로 한다.

**주의:** Vercel 프리뷰 배포(`*.vercel.app`)는 등록 도메인이 달라 로그인이 동작하지 않는다.
프리뷰에서 인증 흐름을 테스트하려면 별도 방안이 필요하다.

**딸린 변경 — 로그인 후 복귀 지점.** 프론트와 API 가 다른 호스트가 되면서
`returnTo` 가 상대 경로만 허용하던 방식이 깨졌다. 상대 경로로 302 를 보내면
화면이 없는 API 호스트(`api.moeum.store`)로 돌아간다.

허용 출처 목록에 있는 **절대 URL 을 받도록** 바꿨다. 판매자는 `studio` 로,
구매자는 `www` 로 각자 돌아가야 하므로 목록 대조가 필요하다.
아무 절대 URL 이나 받으면 열린 리다이렉트가 되므로 목록에 없으면 기본값으로 보낸다.

CORS 허용 · Origin 검증 · `returnTo` 판정이 이제 `AllowedOrigins` 하나를 공유한다.
셋이 갈라지면 "CORS 는 통과했는데 필터가 막는" 식으로 어긋난다.

## D-019. 카카오 앱은 하나만 쓴다

**결정:** 판매자 사이트(`studio.moeum.store`)와 구매자 사이트(`www.moeum.store`)가
따로 있지만 **카카오 개발자 앱은 1개**를 공유한다.

**이유:** 카카오 회원번호는 앱마다 다르게 발급된다. 앱을 나누면 같은 사람이
판매자 앱에서 `999999`, 구매자 앱에서 `111111` 을 받는다.
두 값이 같은 사람이라는 정보는 어디에도 없다 — 카카오가 주지 않고,
이 서비스는 이메일도 전화번호도 받지 않는다.

**사이트가 둘이라고 앱도 둘일 이유는 없다.** 앱 하나에 Redirect URI 와
플랫폼 도메인을 여러 개 등록할 수 있고, 이 프로젝트는 서버 리다이렉트 방식이라
Redirect URI 가 애초에 프론트 주소가 아니라 API 주소(`api.moeum.store`) 하나다.

**역할 분리는 이미 DB 에서 하고 있다.** `seller` 와 `buyer` 는 별개 테이블이고
UNIQUE 는 각 테이블 안에서만 걸린다. 같은 `kakao_id` 가 양쪽에 존재할 수 있다
(운영 DB 에서 확인함). 카카오 앱은 신원 층위, 테이블은 역할 층위다.

**대안과 비교**

| | A. 앱 1개 | B. 앱 2개 |
|---|---|---|
| 한 계정으로 판매자·구매자 겸업 | 같은 사람으로 기록 | **남남으로 기록** |
| studio ↔ www 로그인 공유 | 자동 (같은 등록 도메인) | 오염 위험, 별도 대응 필요 |
| 추가 구현 | 없음 | 세션 역할 검증 또는 API 호스트 분리 |
| 얻는 것 | — | 동의화면 브랜딩 분리 |
| 나중에 되돌리기 | 나눌 수 있음 | **합칠 수 없음** |

B 가 주는 것은 동의화면 브랜딩뿐이다. 동의항목이 양쪽 다 닉네임 하나라
실질 차이가 없고, 그 대가로 동일인 식별을 영구히 잃는다.

**주의:** 겸업 지원 여부는 기능 명세에 없던 항목이다. 코드가 이미 "겸업 가능"으로
구현돼 있었고 이 결정은 그것을 명시화한 것이다. 기획에서 "판매자와 구매자는
완전히 분리된 사용자"로 확정하면 재검토한다. **단, 그 시점에 이미 쌓인 계정은
되돌릴 수 없다는 점을 감안해야 한다.**

## D-020. 세션을 톰캣 인메모리에서 Spring Session JDBC 로 옮긴다

**결정:** 세션을 MySQL 에 저장한다. Redis 는 넣지 않는다.

**문제:** 세션이 톰캣 힙에만 있어서 앱 컨테이너가 교체되면 통째로 사라진다.
배포할 때마다 전원 로그아웃된다. 4단계가 붙으면 이 유실이 "다시 로그인" 이 아니라
"결제 도중 튕김" 이 되므로 그 전에 처리한다.

**왜 Redis 가 아닌가**

*앱이 한 대라 Redis 의 실질 이득이 안 살아난다.* Redis 가 나은 점은 속도가 아니라
결제 경로의 MySQL 을 안 건드린다는 격리인데, 그게 값어치를 하려면 세션 조회가
DB 에 부담이 될 만큼 트래픽이 있어야 한다. 앱 한 대에서는 그 지점이 오지 않는다.

*고장 지점을 늘리지 않는다.* MySQL 이 죽으면 세션도 죽지만 그때는 어차피 서비스 전체가
죽는다 — 망가지는 경우의 수가 늘지 않는다. 반면 Redis 는 그것만 죽어도 전원 로그아웃이다.
MySQL 도 앱도 멀쩡한데 아무도 결제를 못 하는 상황이 새로 생긴다.
EBS 스냅샷도 모니터링도 없는 지금, 조용히 죽어도 알아챌 수 없는 구성 요소를 늘리는 것은 값이 있다.

| | JDBC (MySQL) | Redis |
|---|---|---|
| 요청당 비용 | SELECT + UPDATE | HGETALL + EXPIRE (더 빠름) |
| 부하가 가는 곳 | 재고 경합이 일어나는 그 MySQL | 별도 프로세스 |
| 내구성 | 커밋됨 | AOF everysec — 호스트 장애 시 최대 1초 손실 |
| 새 컨테이너 | 0개 | 1개 |
| 고장 지점 | 늘지 않음 | 하나 늘어남 |

**애플리케이션 코드는 바뀌지 않는다.** Spring Session 이 서블릿 필터로
`request.getSession()` 반환 객체만 바꿔치기한다. `HttpSession` 인터페이스가 그대로다.

**카카오 access token 을 세션에서 뺀다.** 세션 속성이 MySQL 에 자바 직렬화 blob 으로
남게 됐는데, 지금 쓰는 곳이 없는 토큰을 그렇게 둘 이유가 없다.
알림톡·프로필 갱신에 필요해지면 그때 암호화해서 별도로 보관한다.

**뒤집히는 조건**

- 앱을 2대 이상 띄울 때 — 세션 조회가 앱 수만큼 늘어 재고 경합과 같은 MySQL 을 놓고 다툰다.
  (그 경우에도 JDBC 로 동작은 한다. 필수가 아니라 유리해지는 것이다.)
- 재고 카운터·레이트리밋 때문에 어차피 Redis 를 들일 때 — 두 번 작업하지 말고 그때 같이 옮긴다.

어느 쪽이든 저장소 구현만 바뀌므로 의존성과 설정 두 줄 교체로 끝난다.

**혼동 주의 — 재고 Redis 와 별개다.** 세션 Redis 는 앱을 몇 대 띄우느냐로 판단하고,
재고 Redis 는 한 상품에 몰리는 양이 DB 행 처리량 한계를 넘느냐로 판단한다 (D-008).
재고의 병목은 `sale_form` 행 하나라 앱 대수와 무관하다.

## D-021. 공개 상품 API 는 판매 폼을 가리키고, 정적 정보와 재고를 나눠 내려준다

**결정:** `GET /products/{id}` 의 `{id}` 는 `sale_form.id` 다. 재고 현황은
`GET /products/{id}/availability` 로 분리하고 `no-store` 를 건다.

**`{id}` 가 판매 폼인 이유:** 재고 · 목표수량 · 마감 · 최소주문금액이 전부 폼 단위다.
`product` 는 폼 안에서 옵션을 묶는 층이지 구매 단위가 아니다. 경로가 `/products` 인 것은
구매자 화면의 용어를 따른 것이고, 실체는 판매 폼이다.

**정적/휘발성을 나눈 이유:** 상품 페이지는 캐시해서 빨리 띄우고 싶은데 재고는 초 단위로 바뀐다.
한 응답에 섞으면 캐시된 재고가 화면에 남고, 그걸 보고 구매를 누르면 홀드에서 품절로 튕긴다.
`Cache-Control: no-store` 를 응답에 직접 실어 중간 프록시까지 막는다 — 프론트 설정에만 맡기지 않는다.

**api-spec 과 달라진 것**

| 스펙 | 구현 | 이유 |
|---|---|---|
| `options[]` 평탄화 | `products[].options[]` | product 가 2개 이상이면 옵션이 뒤섞인다 |
| `recruitDeadline` = "D-5" | `recruitDeadline`(시각) + `recruitDDay`(숫자) | 표기는 화면이 정한다. 서버는 값을 준다 |
| `status` 저장값 | 파생값 | 아래 참고 |

**status 는 저장하지 않고 파생한다.** DB 는 `DRAFT · SELLING · PAUSED · CLOSED · ENDED` 이고
공개 응답은 `SELLING · SOLD_OUT · CLOSED · PAUSED` 다.

- `DRAFT` 는 **404** 로 숨긴다. 403 이면 "그 id 에 폼이 있다"는 사실이 새어 나가
  id 를 훑어 셀러가 준비 중인 상품을 알아낼 수 있다
- `SOLD_OUT` 은 재고에서 파생한다 (`stock_max - held - sold <= 0`)
- `closes_at` 이 지났으면 DB 가 아직 `SELLING` 이어도 `CLOSED` 로 내린다.
  마감 배치가 1분마다 돌아 그 틈이 반드시 생긴다

**`recruitedCount` 는 확정 주문 수량(`sold`)이다 — 홀드를 세지 않는다.**
홀드는 15분 뒤 만료될 수 있고, 세면 모집 숫자가 뒤로 간다. 분모인 `target_qty` 가
수량이므로 단위도 맞는다. `progress_public = false` 거나 `SOLO` 면 `null` 로 감춘다 —
다만 재고는 감추지 않는다. 스티퍼 상한을 그릴 수 없다.

**셀러 이름은 `seller.store_name` 을 새로 둔다 (V3).**
있던 것은 `store_slug`(URL 식별자)와 `representative_name`(대표자 실명)뿐이었다.
실명을 공개 상품 페이지에 노출할 수 없다. 이 컬럼이 없던 시절 셀러는 값이 비어 있어
`store_slug` 로 대체한다 — 이름이 비었다고 개인정보로 대체하지 않는다.

**이미지는 URL 입력이다.** 파일 업로드 인프라가 없다(S3 도 업로드 엔드포인트도 없다).
`sale_form_image` 에 셀러가 외부 URL 을 넣는다. 업로드가 붙어도 이 컬럼을 채우는 주체만 바뀐다.

**공구 마감 배치는 상태 전이만 한다.** `closes_at` 지난 `SELLING` → `CLOSED` 한 문장이다.
`shortfall_policy`(CANCEL · EXTEND · PROCEED) 적용은 6단계다 — CANCEL 은 이미 1차금이 결제된
주문을 환불한다는 뜻인데 결제도 환불도 없고, EXTEND 의 연장 횟수 규칙도 기획 미확정이다.
재고 확보 쿼리가 `closes_at` 을 직접 보므로 배치가 늦어도 초과 판매는 나지 않는다.
이 배치는 화면에 보이는 상태를 맞추는 일이다.

**남은 것:** 판매 폼을 `DRAFT` 에서 `SELLING` 으로 올리는 흐름이 아직 없다.
지금은 테스트가 직접 UPDATE 로 올린다. 판매 시작 · 일시중지 API 가 필요하다.

## D-022. 이미지는 presigned URL 로 브라우저가 S3 에 직접 올리고, DB 에는 키만 저장한다

**결정:** 서버는 presigned PUT URL 만 발급한다. 파일 바이트는 서버를 지나가지 않는다.
`sale_form_image` 에는 **S3 객체 키**를 저장하고 읽기용 주소는 응답에서 조립한다.

**서버가 중계하지 않는 이유:** t3.small 한 대에 JVM 과 MySQL 이 같이 살고 스왑에 기대는 구성이다
(deployment.md). 이미지를 중계하면 그 힙을 바이트가 지나가 동시 업로드 몇 개에 메모리가 마르고,
대역폭도 EC2 를 두 번 탄다.

```
1. 프론트 → 서버   POST /seller/sale-forms/images/upload-url
2. 프론트 → S3     PUT (파일). 우리 서버를 거치지 않는다
3. 프론트 → 서버   판매 폼 저장 요청의 images[] 에 objectKey 를 실어 보낸다
```

**대신 서버가 바이트를 못 보므로 검증 지점이 발급 시점뿐이다.** 셋을 서명에 넣는다.

- **키** — 서버가 만든다 (`sale-forms/{sellerId}/{uuid}.{ext}`). 클라이언트가 정하게 두면
  남의 경로를 지정해 덮어쓸 수 있다. 그래서 요청에 파일 이름을 받지 않는다
- **Content-Type** — 허용 목록(jpeg · png · webp · gif) 밖이면 발급하지 않는다
- **Content-Length** — 서명에 넣는다. 다른 크기로 올리면 S3 가 서명 불일치로 거부하므로
  크기 상한이 실제로 강제된다. presigned POST 가 아니라 PUT 을 쓰는데도 상한이 서는 이유다

URL 유효 시간은 5분이다. 새어 나가도 그 시간만 쓸 수 있다.
심사를 통과한 셀러만 발급받는다.

**키만 저장하는 이유 (V4).** V3 에서 `url VARCHAR(500)` 으로 넣었던 것을 `object_key` 로 바꿨다.
전체 URL 을 저장하면 버킷 이름을 바꾸거나 CloudFront 를 앞에 세울 때 쌓인 행을 전부 고쳐야 한다.
키만 두면 `ImageStorage.publicUrl` 한 곳과 설정 한 줄만 바뀐다.
쌓인 데이터가 없는 시점이라 이전 작업도 필요 없었다.

**자격증명은 설정에 두지 않는다.** EC2 인스턴스 역할(`moeum-ec2`)이 준다.
이 프로젝트는 배포도 OIDC 로 하고 시크릿도 Parameter Store 에서 받는다 (D-017).
여기만 액세스 키를 박으면 그 원칙이 깨진다. 서명은 로컬 계산이라 테스트는 더미 키로 검증한다.

**설정이 비면 업로드만 꺼진다.** `S3_BUCKET` 이 없으면 발급 요청이 `STORAGE_NOT_CONFIGURED`
(503)로 떨어지고 나머지는 정상 동작한다. prod 프로파일에도 기본값을 비워 두었다 —
파라미터 하나가 없다고 배포가 기동 실패로 죽으면 안 된다 (`KAKAO_CLIENT_SECRET` 과 같은 이유).

**남은 것 — 고아 파일.** presigned 로 올렸는데 판매 폼을 저장하지 않으면 그 파일은
아무 데서도 참조되지 않고 버킷에 남는다. 수명주기 규칙으로 걷어내야 한다.
지금은 규칙을 걸지 않았다.

**AWS 쪽 준비 (저장소 밖 작업)**

```bash
# 버킷 (퍼블릭 읽기). 트래픽이 붙으면 CloudFront 를 앞에 세우고 public-base-url 만 바꾼다
aws s3api create-bucket --bucket moeum-images --region ap-northeast-2 \
  --create-bucket-configuration LocationConstraint=ap-northeast-2

# 프론트 도메인에서 PUT 할 수 있도록 CORS. 빠뜨리면 브라우저가 막는다
# 인스턴스 역할에 PutObject 만 준다. 삭제·목록 권한은 주지 않는다
```

Parameter Store 에 `S3_BUCKET`, `S3_PUBLIC_BASE_URL` 을 넣고 재배포하면 켜진다.

## D-023. 재결제는 실패한 payment 행을 재사용한다

**결정:** 결제가 실패해 다시 시도할 때, 새 행을 만들지 않고 기존 행의
`session_id` 와 `status` 를 갈아끼운다. `uk_payment_group_phase` 유니크는 그대로 둔다.

**문제:** 스키마가 한 주문묶음의 차수당 payment 행을 하나로 제한한다.

```sql
UNIQUE KEY uk_payment_group_phase (order_group_id, phase)
```

카드 한도 초과·결제창 이탈·본인인증 실패로 첫 시도가 `FAILED` 로 끝나면 그 행이 자리를 차지해
두 번째 시도의 행을 INSERT 할 수 없다. 재시도는 새 point3 세션을 요구하므로
(실패한 sessionId 는 재사용 불가) 새 sessionId 를 담을 자리가 없다.

재고 홀드는 15분간 살아 있다. 그 안에 다시 결제할 수 없으면 구매자는 장바구니부터 다시 해야 하고,
마감이 있는 공동구매에서 그건 그대로 이탈이다.

**왜 유니크를 완화하지 않는가:** 유니크를 풀면 "성공한 결제는 하나뿐" 이라는 보장이
DB 제약에서 애플리케이션 코드로 내려온다. MySQL 은 부분 유니크 인덱스가 없어
"status='CAPTURED' 인 행은 하나" 를 제약으로 표현할 수 없다. 결제 도메인에서
중복 방지를 코드에 맡기는 건 손해다. 이력은 `payment_event` 가 상태 전이마다 행을 남기므로
payment 테이블은 "현재 상태" 만 들고 있으면 된다.

**⚠️ 재사용은 `FAILED` 일 때만 허용한다.**

`CAPTURE_PENDING` 을 덮어쓰면 안 된다. 그건 승인 결과를 모르는 상태이고,
그 기록이 사라지면 **실제로 출금됐는데 추적할 방법이 없어진다** (CLAUDE.md 규칙 3·4, D-004).
`CREATED` · `CAPTURED` 도 덮어쓰지 않는다 — 진행 중이거나 이미 끝난 결제다.

재사용 시점에 `payment_event` 로 전이를 남겨 몇 번째 시도인지 추적할 수 있게 한다.

**아직 구현하지 않았다.** `PaymentService` 착수 시 이 규칙으로 만든다.

## D-024. 취소 시 재고를 되돌릴지는 발주 여부로 가른다

**결정:**

```
SOLO              → 되돌린다
GROUP · 마감 전   → 되돌린다
GROUP · 마감 후   → 되돌리지 않는다
```

**기준은 판매 유형이 아니라 발주가 나갔는가다.** SOLO 는 창고에 실물이 있는 상품이라
취소되면 물건이 진짜로 돌아온다. GROUP 은 "모집된 몫" 이고, 마감 후에는 셀러가
그 수량으로 이미 발주를 넣었다 — 되돌려서 다시 팔리면 셀러가 없는 물건을 팔게 된다.

GROUP 이라도 마감 전이면 발주 전이므로 되돌리는 것이 맞다.

**마감 전 GROUP 을 되돌려야 하는 이유가 하나 더 있다.** 목표 100 에 99명이 모였는데
1명이 취소한 상황에서, 되돌리면 그 자리를 다른 사람이 채워 목표를 달성할 수 있다.
안 되돌리면 그 자리는 영원히 비어 있고 공구는 미달로 끝난다. 셀러에게 손해다.

**부수 효과 — 목표수량 판정이 저절로 정확해진다.**
마감 전 취소가 `sold` 에서 빠지므로 마감 시점의 `sold` 가 곧 실제 결제자 수다.
`sold` 를 그대로 두면 "99명인데 100으로 판정" 이 생겨 미달 공구가 진행돼 버린다.
별도의 `canceled` 컬럼을 두지 않아도 되는 이유다.

마감 후 취소는 `sold` 에 남지만 목표 판정이 이미 끝난 뒤라 왜곡이 없다.
"68/100 모집 완료" 로 굳은 숫자가 사실에 맞다.

**구현:** `sale_form.sale_type` 과 `status` 두 값만 보면 되고,
재고 확보와 같이 조건부 UPDATE 한 방으로 처리한다.

## D-025. 구매자 취소 구간은 판매 유형으로 가른다

**결정:**

```
GROUP  PAID · RECRUITING · CLOSED 까지          PRODUCING 부터 불가
SOLO   ARRIVED 까지 (= 발송 전)                 SHIPPED 부터 불가
```

**기준은 D-024 와 같다 — 셀러가 되돌릴 수 있는가.** GROUP 은 마감된 수량으로 발주가
나가므로 발주가 시작되면 한 명이 빠지는 만큼 셀러가 손해를 본다. SOLO 는 이미 있는
재고를 파는 것이라 발주라는 단계가 없고, 물건이 나가기 전이면 창고에 그대로 있다.

**취소 구간과 재고 되돌림은 다른 질문이다.** GROUP 은 마감(`CLOSED`)돼도 취소는 되지만
그 자리를 다시 팔 수 없어 재고는 되돌리지 않는다 (D-024). 두 규칙이 같은 선에서
갈리지 않으므로 한쪽 코드로 합치지 않는다.

**⚠️ SOLO 컷은 '배송 준비' 가 아니라 '발송' 을 기준으로 뒀다.**
PM 이 정한 문구는 "배송 준비 전까지" 인데, 현재 상태 머신에는 배송 준비 단계가 없고
`ARRIVED`(입고) 다음이 곧 `SHIPPED`(발송)다. 입고에서 자르면 **2차금을 결제하자마자
취소가 막히므로** 더 늦은 쪽으로 뒀다. 7단계에서 배송 상태가 들어오면
`RefundPolicy.SOLO_CANCELABLE` 에서 그 값을 빼는 것으로 컷이 앞당겨진다.

### 한 번의 "취소" 가 결제 취소 두 건이 된다

1차금과 2차금이 별도 세션이라 `payment` 행이 둘이고 각각 따로 취소해야 한다.
`OrderRefundService` 가 이 번역을 맡는다.

| 상황 | 처리 |
|---|---|
| 1차금 확정 거절 | 2차금을 보내지 않는다. 상품값은 받은 채 배송비만 돌려주게 된다 |
| 1차금 미확정(`PROCESSING`) | 2차금은 그대로 보낸다. 실패가 아니라 결과를 모르는 것뿐이다 |
| 한 건이라도 미확정 | 전체가 `PROCESSING`. 성공한 쪽만 보고 끝내면 나머지가 묻힌다 |

**재고 되돌림과 주문 취소 표시는 1차금 쪽에서만 한다.** 두 건 다 확정되므로
양쪽에서 되돌리면 재고가 두 번 돌아간다.

### 배송비

**남은 폼이 있으면 유지, 마지막 폼까지 취소되면 함께 환불한다** (domain.md).
배송비는 묶음당 1회이고 2차금에 실려 있으므로, 마지막 취소의 2차금 환불액에 더한다.
2차금을 아직 결제하지 않았으면 배송비를 받은 적이 없으니 돌려줄 것도 없다.

### 곁다리 — 1차금이 배송비를 이중 청구하고 있었다

`OrderGroup.firstPaymentAmount()` 가 `deposit1Total + shippingFee` 였다.
2차금도 배송비를 더하므로 **같은 배송비를 두 번 청구**한다. api-spec 6절
("B5 청구액은 옵션가뿐")과 어긋나고, 이 상태로는 취소 시 배송비를 어느 쪽에서
돌려줘야 하는지도 정할 수 없다. `deposit1Total` 만 청구하도록 고쳤다.

## D-026. 목표수량 미달 취소는 마감 배치와 분리한다

**결정:** 마감 배치는 `SELLING → CLOSED` 상태 전이만 하고, 미달 처리는
`ShortfallCancelBatch` 가 CLOSED 된 폼을 다시 훑어 처리한다.

**이유는 트랜잭션이다.** 미달 취소는 point3 를 부르는데 마감 배치는 조건부 UPDATE 한 방을
트랜잭션 안에서 돌린다. 같은 자리에 넣으면 외부 호출이 트랜잭션 안으로 들어온다
(CLAUDE.md 규칙 1). 배치를 나누면 마감은 여전히 UPDATE 한 방이고, 취소는 트랜잭션 밖이다.

```
CANCEL   그 폼의 주문을 전부 취소한다
PROCEED  그대로 진행한다
EXTEND   ★ 구현하지 않았다 — 연장 횟수·기간 규칙이 기획 미확정이다 (domain.md)
```

`shortfall_policy` 가 비어 있으면 `PROCEED` 로 본다. **정책이 없다고 남의 돈을 돌려주지 않는다.**

### 두 번 돌면 이중 환불이다

이미 받은 돈을 돌려주는 배치라 재실행 방어가 이 설계의 전부다.

**`sale_form.shortfall_done_at` 을 찍는다** (V5). "취소되지 않은 주문이 남아 있는가" 로
판정하면 두 가지가 깨진다 — 확정 거절된 건을 영원히 다시 시도하고, 결과를 모르는
(`PROCESSING`) 건이 있는 동안 다시 보내 두 번 환불한다.

**정책과 결과에 상관없이 찍는다.** 미달이 아니어도, PROCEED 여도, 취소가 미확정으로 끝나도
찍는다. 미확정 건은 취소 대사 배치가 조회 → resume 으로 끝낸다 — 그게 취소에서 유일하게
안전한 재시도 수단이다.

조회 자체도 `FOR UPDATE SKIP LOCKED` 로 잠근다. 두 인스턴스가 같은 폼을 집으면
같은 주문에 취소를 두 번 보낸다.

### 한 건이 터져도 멈추지 않는다

주문마다 예외를 잡는다. 앞에서 멈추면 뒤의 구매자들은 돈을 못 받은 채 다음 주기를
기다리는데, `shortfall_done_at` 때문에 그 주기는 오지 않는다.

### 취소 구간(D-025)을 보지 않는다

구매자 취소는 공구 마감 전까지지만, 미달 취소는 **발주가 나갔든 아니든 돌려준다.**
구매자 잘못이 아니라 폼이 성립하지 않은 것이다. `OrderRefundReader.systemPlan` 이
소유권 검증과 `RefundPolicy` 를 모두 건너뛰는 이유다.

재고는 되돌리지 않는다. 마감된 GROUP 폼이라 D-024 의 규칙이 그대로 적용되고,
어차피 그 자리를 다시 팔 수 없다.

## D-027. Outbox 릴레이의 임대와 백오프는 컬럼 하나로 겸한다

**결정:** `outbox.next_attempt_at` 하나가 "실패 후 언제 다시" 와 "지금 누가 처리 중" 을 둘 다 맡는다 (V6).

원래 스키마에는 `retry_count` 만 있었다. 다음 시도 시각을 담을 곳이 없어
`created_at` 으로 계산하려 하면 — 그건 적재 시각이지 마지막 시도 시각이 아니라 —
실패가 쌓여도 간격이 벌어지지 않고 **1초마다 계속 두드리게 된다.**

```
집을 때   next_attempt_at = now + 1분   (임대)
실패하면  next_attempt_at = now + 백오프  10초 → 20 → 40 → … → 1시간에서 멈춤
조회      WHERE status='PENDING' AND next_attempt_at <= now
```

**임대가 필요한 이유는 발송이 트랜잭션 밖이기 때문이다.** `FOR UPDATE SKIP LOCKED` 로
집어도 claim 트랜잭션이 커밋되는 순간 락이 풀린다. 그 뒤 발송하는 동안 다른 인스턴스가
같은 행을 집으면 **알림톡이 두 번 나간다.** 집으면서 시각을 앞으로 밀어 두면 그 사이에는
아무도 못 집고, 프로세스가 죽어도 임대가 만료돼 자동으로 다시 잡힌다.
`SENDING` 같은 상태를 새로 만들지 않아도 되는 이유다.

### 적재는 호출자의 트랜잭션에 합류한다

`OutboxRecorder` 에는 **`@Transactional` 이 없다.** 이건 빠뜨린 게 아니라 이 클래스의 전부다 —
사실과 알림이 같이 커밋돼야 "결제됐는데 알림이 없음" 도 "알림만 있고 결제가 없음" 도 생기지 않는다.
`REQUIRES_NEW` 를 붙이면 결제가 롤백돼도 알림만 남아 **결제되지 않은 주문의 결제 완료 알림**이 나간다.

`payload` 직렬화가 실패해도 예외를 던지지 않는다. 여기서 던지면 호출자 트랜잭션이 통째로
롤백된다 — 알림 하나 못 만든 대가로 결제 확정이 날아가는 것은 맞바꿀 만한 거래가 아니다.

### 적재 지점은 전부 멱등 가드 안쪽이다

| 이벤트 | 적재 위치 | 가드 |
|---|---|---|
| `ORDER_PAID` · `SECOND_PAID` | `PaymentWriter.finalizeCapture` | `markCaptured()` 가 false 면 그대로 반환 |
| `SECOND_PAYMENT_DUE` | `SaleFormService.markArrived` | `markArrived()` 가 false 면 건너뜀 + 묶음 전체 입고 확인 |
| `REFUND_COMPLETED` | `RefundWriter.complete` | `markCompleted()` 가 false 면 그대로 반환 + 1차금 차수에서만 |

밖으로 빼면 대사 배치가 확정된 건을 다시 훑을 때마다 알림이 쌓인다.

### DEAD 는 버리는 게 아니라 넘기는 것이다

8번 실패하면 `DEAD` 로 내리고 더 시도하지 않되, `ERROR` 로 로그를 남긴다.
**알림이 곧 결제 요청이라 조용히 버릴 수 없다** — 구매자는 잔금을 낼 줄 모르고
셀러는 미수로 남은 이유를 알 수 없다.

### 지금은 로그만 찍는다

`LoggingNotificationSender` 가 성공으로 치고 로그만 남긴다. 카카오 알림톡 계정이 없어서다.
**이걸 쓰는 동안 구매자에게는 아무것도 가지 않는다.** outbox 행은 `SENT` 로 넘어가므로
나중에 알림톡을 붙여도 그 사이 건들은 다시 나가지 않는다.
`moeum.notify.provider` 로 갈아 끼운다.

## D-028. 테스트 JVM 타임존을 Asia/Seoul 로 고정한다

**결정:** `build.gradle` 의 test task 에 `systemProperty 'user.timezone', 'Asia/Seoul'`.

**계기:** 로컬에서 281개가 전부 통과하는데 **GitHub Actions 에서만 3개가 깨졌다.**
러너는 UTC 이고 개발 PC 와 운영 컨테이너는 KST 라서, 여태 우연히 맞아 있었다.

```
expected: 2026-09-08T12:00:10
 but was: 2026-09-08T21:00:10     ← 정확히 9시간
```

**원인은 쓰기와 읽기가 다른 경로를 타는 것이다.** `hibernate.jdbc.time_zone: Asia/Seoul`
은 JDBC 연결이 KST 라고 알려 주는 설정이라, Hibernate 는 `LocalDateTime` 을 저장할 때
**JVM 기본 타임존 → KST** 로 변환한다. JVM 이 KST 면 변환량이 0 이라 아무 일도 없지만,
UTC 면 +9 가 붙는다. 그 값을 `JdbcTemplate` 으로 직접 읽으면 변환이 한 번만 일어난
상태라 9시간 어긋난 채로 나온다.

**운영에는 이 문제가 없다.** 앱 컨테이너가 `TZ=Asia/Seoul` 과
`-Duser.timezone=Asia/Seoul` 로 고정돼 있는 것을 확인했다. 즉 이건 운영 버그가 아니라
**테스트 환경이 운영과 달라서 생긴 것**이고, 고칠 곳은 테스트 쪽이다.

**단언을 느슨하게 바꾸지 않았다.** 시각 비교를 걷어내면 백오프가 실제로 뒤로 밀리는지
확인할 방법이 없어진다 — 그게 이 테스트의 전부다. 대신 환경을 운영에 맞췄다.

**부수 효과:** 개발자 로컬 타임존이 무엇이든 같은 결과가 나온다.

**교훈:** `NOW()` 같은 DB 시각과 Hibernate 가 쓴 컬럼을 섞어 비교하는 코드는
JVM 타임존에 따라 결과가 달라진다. 새 배치를 만들 때 이 조합을 피한다.

## D-029. 셀러 페이지 목록은 캐시하지 않는다

**결정:** `GET /stores/{storeSlug}` 는 헤더와 상품 목록을 한 번에 주고, 응답 전체를
`no-store` 로 내린다.

상세는 정적 정보(`/products/{id}`)와 휘발성(`/availability`)을 나눠 두었다 (D-021).
목록에서 같은 방식을 쓰면 **카드 수만큼 조회가 나간다** — 카드마다 "모집 68/100" 과
"재고 5개" 가 찍히기 때문이다. 20장이면 왕복이 21번이다.

그래서 반대로 갔다. 목록은 통째로 캐시하지 않는다. **캐시된 재고를 보고 들어가면
홀드에서 품절로 튕긴다**는 것이 D-021 의 이유였고, 그 이유는 목록에서도 같다.

대신 한 번에 가져갈 수 있는 수를 50 으로 제한한다. 캐시가 없으니 페이지 크기가 곧 DB 부하다.

### 노출 범위

| | |
|---|---|
| 미승인 셀러 | 404. 심사 전 상점은 공개 주소가 없는 것으로 본다 |
| `DRAFT` 폼 | 목록에서 제외. 셀러 본인 화면에만 보인다 |
| 마감된 폼 | **보여준다.** 지난 공구를 확인할 수 있어야 한다 |
| 정렬 | 판매 중 먼저, 그다음 최신순 |

마감된 폼을 위에 두면 지금 살 수 있는 것을 찾으려고 스크롤해야 한다.

### 검색어의 와일드카드를 escape 한다

`LIKE` 에 그대로 끼워 넣으면 구매자가 친 `%` 가 와일드카드로 동작해 상품 전체가 걸린다.
`%` · `_` · `!` 를 escape 하고 쿼리에서 `ESCAPE '!'` 로 받는다.

### 대표가는 가장 싼 옵션의 1차금 + 2차금

카드에는 가격이 하나만 찍힌다. 배송비는 넣지 않는다 — 묶음당 1회라 상품 단위로 나눌 수 없다.

### 셀러 공개 프로필 (V7)

`bio` · `social_url` · `profile_image_key` 를 추가했다. 지금까지 seller 에 있던
공개 가능한 값은 `store_name` · `store_slug` 뿐이라 헤더를 채울 수 없었다.

**같은 테이블의 심사용 값들과 성격이 정반대다.** `representative_name` · `phone` ·
`email` · `business_no` · `settlement_account` 는 구매자에게 새면 안 되고,
이 셋은 구매자에게 보이라고 받는 값이다. 응답 DTO 에서 갈린다.

`social_url` 은 스킴을 `http(s)` 로 강제한다. 헤더 버튼에 그대로 링크가 걸리므로
`javascript:` 같은 값이 들어오면 안 된다.

`profile_image_key` 는 클라이언트가 키를 그대로 보내오므로 **소유자를 확인한다** —
키가 `{prefix}/{sellerId}/...` 형태라 접두사만 봐도 판별된다. 확인하지 않으면
남의 이미지를 자기 프로필로 걸어 둘 수 있다.

### 찜(하트)은 목록과 분리한다 (V8)

와이어프레임의 카드마다 하트가 있지만 **목록 응답에는 넣지 않는다.**
`wished` 를 실으면 이 응답이 사용자별로 갈려 모두에게 같은 것을 줄 수 없게 된다.
셀러 페이지는 로그인 없이도 보이는 화면이다.

```
GET    /me/wishlist            하트를 칠할 폼 id 목록
PUT    /me/wishlist/{id}       찜
DELETE /me/wishlist/{id}       해제
```

프론트가 목록을 그린 뒤 이 목록으로 하트만 칠한다.

**찜과 해제 둘 다 멱등하다.** 하트는 연타되는 버튼이라 두 번 눌렀다고 409 를 돌려주면
화면이 깜빡인다. 같은 상태로 만들어 달라는 요청으로 본다.

**멱등을 예외로 구현하면 안 된다.** `DataIntegrityViolationException` 을 잡는 방식은
여기서 통하지 않는다 — 유니크 위반이 나는 순간 트랜잭션이 rollback-only 로 표시돼서,
예외를 잡아도 커밋 시점에 `UnexpectedRollbackException` 으로 터진다.
`INSERT ... ON DUPLICATE KEY UPDATE id = id` 로 **DB 가 중복을 삼키게** 한다.
`INSERT IGNORE` 는 쓰지 않는다 — FK 위반까지 삼켜서 없는 구매자·폼으로 찜이 조용히 사라진다.

찜은 판매 폼 단위다. 재고 · 마감 · 목표수량이 전부 폼 단위라 구매자가 보는 '상품'의
실체가 폼이고(D-021), 찜도 같은 단위여야 한다.

주문한 적 없는 사용자도 찜할 수 있다 — `buyer` 행이 그 시점에 만들어진다.
하트부터 누르고 나중에 사는 것이 정상적인 순서다.

마감된 폼의 찜은 유지한다. 지난 공구를 찜해 둔 채 다음 회차를 기다리는 것이 자연스럽다.

## D-030. 셀러 설정 화면(G12)을 와이어프레임에 맞춘다

현황판을 와이어프레임과 대조하면서 **설정 화면의 두 칸이 서버에 없다**는 것이 드러났다.

### 구매자 문의 연락처를 따로 둔다 (V9)

`seller.phone` 이 이미 있지만 그건 **심사·정산 담당자가 연락하는 번호**다.
대표자 개인 번호일 수 있어 구매자에게 그대로 내보내면 안 된다.
화면의 '구매자 문의 연락처' 칸은 셀러가 공개하겠다고 적는 값이라 성격이 다르다.

`public_contact` 를 새로 뒀다. **비어 있다고 `phone` 으로 대신 채우지 않는다** —
그 한 줄이 개인정보 유출이 된다. 안 적었으면 안 적은 채로 내보낸다.

전화번호 형식을 강제하지 않는다. 오픈채팅 링크나 이메일을 적는 셀러가 있고 화면도 자유 입력이다.

### 판매공간 주소를 바꿀 수 있게 한다 (SALE-105)

`PUT /seller/me/profile` 이 `storeSlug` 를 못 바꾸게 막고 있었다.
**이미 뿌린 링크가 죽기 때문**이었는데, 와이어프레임은 셀러가 직접 입력하는 화면이다.
화면이 정답이므로 막지 않는다.

되돌릴 수 없는 변경이라 두 가지를 붙였다.

- 중복은 409 (`DUPLICATE_STORE_SLUG`). 미리 확인하되 최종 판정은 `uk_seller_slug` 에 맡긴다 —
  두 요청이 동시에 통과할 수 있다
- 변경 시 `sellerId, 이전 → 이후` 를 로그로 남긴다.
  "어제까지 되던 링크가 안 된다"는 문의가 오면 이 로그가 유일한 단서다

**옛 주소 리다이렉트는 넣지 않았다.** 하려면 주소 이력 테이블이 필요하고,
언제까지 살려 둘지도 정해야 한다. 화면이 요구하는 것은 변경까지다.

같은 주소를 그대로 보내면 아무 일도 하지 않는다. 설정 화면은 전체 폼을 보내므로,
주소를 안 건드린 저장이 중복으로 튕기면 저장 자체가 안 된다.

### 여전히 못 바꾸는 것

대표자 실명 · 사업자번호 · 정산계좌 · 이메일은 승인의 근거다.
셀러가 이 화면으로 갈아 끼울 수 있으면 심사가 무의미해진다.
바꿔야 할 일이 생기면 운영자를 거친다.

## D-031. 스웨거 설명은 @Schema 로 달고, 빠지면 테스트가 잡는다

**계기:** 프론트에서 "`q` 나 `bio` 같은 이름만 보여서 뭘 넣어야 할지 모르겠다"는 말이 나왔다.

**springdoc 은 javadoc 을 읽지 않는다.** 코드에 주석을 아무리 잘 달아도 스웨거에는
필드 이름만 나온다. `@Schema(description = ...)` 를 붙여야 문서에 실린다.

DTO 28개와 컨트롤러 12개에 전부 달았다. 설명은 **프론트가 읽을 문장으로** 쓴다 —
코드 주석의 "왜 이렇게 짰는가"와는 다른 글이라 javadoc 을 그대로 노출하지 않았다.
therapi 로 javadoc 을 자동 노출하는 방법도 있지만, 그러면 트랜잭션 rollback-only 같은
내부 사정이 공개 문서로 새어 나간다.

### 붙였는지를 테스트가 지킨다

`OpenApiDocTest` 가 `/v3/api-docs` 를 받아서 **설명이 빠진 속성·파라미터·엔드포인트를
전부 찾아낸다.** 새 DTO 를 만들면서 빠뜨리면 CI 에서 걸린다.

이걸 만들자마자 세 가지가 드러났다.

**① 인증 엔드포인트마다 `?user` 라는 가짜 쿼리 파라미터가 문서에 있었다.**
`@LoginUser SessionUser user` 는 세션에서 꺼내는 값인데 springdoc 이 요청 파라미터로 읽었다.
**프론트가 이걸 보고 user 를 보내려 했을 것이다.** `SpringDocUtils.addAnnotationsToIgnore`
로 지웠다.

**② `ErrorResponse` 의 설명이 통째로 비어 있었다.** 모든 실패 응답이 이 형식인데
`code` 와 `message` 의 차이가 문서에 없었다 — 화면 분기는 `code` 로 해야 한다.

**③ 판매 폼 생성의 `images` 주석이 낡아 있었다.** "업로드 인프라가 아직 없어 외부에
호스팅된 URL 을 받는다" 라고 돼 있는데, D-022 이후로는 presigned 업로드로 받은
objectKey 를 넣는다. 문서에 그대로 나갔으면 프론트가 URL 을 넣었을 것이다.

### 짧은 이름은 표본으로 한 번 더 못 박는다

`bio` · `publicContact` · `dDay` · `price` · `saleFormIds` 처럼 이름만으로 뜻이 안 서는
필드는 설명에 특정 낱말이 들어 있는지까지 확인한다. 설명이 "있기만" 하고 뜻이 없는
상태를 막으려는 것이다.

## D-032. 무료배송 기준은 상품 총액으로 보고, 주문 시점에 굳는다

**계기:** `Seller.shippingFeeFor(orderAmount)` 는 처음부터 있었는데 **아무도 부르지 않았다.**
주문 생성은 `seller.getShippingFee()` 를 그대로 썼다.

그동안 `freeShippingOver` 는 장바구니 · 상품상세 · 셀러페이지 **세 군데 응답에 실려 나갔다.**
구매자는 "5만원 이상 무료배송" 을 보고 2차금에서 배송비를 냈다는 뜻이다.
실결제가 시작되기 전이라 아직 잘못 청구된 사람은 없다.

### 기준은 상품 총액 (1차금 + 2차금)

배송비는 뺀다. 넣으면 배송비 덕분에 배송비가 면제되는 순환이 된다.
api-spec 이 옵션가를 `deposit1 + deposit2` 로 정의하고 배송비를 거기서 빼는 것과 같은 기준이다.

**1차금만 세지 않는다.** 잔금이 큰 공구에서는 상품값이 기준을 넘는데도 배송비가 붙는다.

경계는 **이상**이다 — 화면 문구가 "이 금액 이상" 이라 딱 맞을 때 붙으면 안내와 다르다.

### 배송비는 생성자에서 정할 수 없다

무료배송 기준이 상품 총액을 보는데, 그 합계는 `addOrder` 가 다 끝나야 나온다.
생성 시점에는 0 원이라 늘 미달로 판정된다. 그래서 항목을 다 담은 뒤
`applyShippingFee` 로 확정한다.

### 한 번 정해지면 굳는다

나중에 폼 하나를 취소해서 총액이 기준 아래로 떨어져도 **소급해서 배송비를 물리지 않는다.**
취소했더니 없던 배송비가 생기는 것은 구매자가 납득할 수 없다.
(반대 방향도 마찬가지다 — D-025 의 배송비 환불 규칙은 `order_group.shipping_fee` 에
굳은 값을 그대로 쓴다.)

### 장바구니도 같은 계산을 내보낸다

`CartResponse.estimatedShippingFee` 를 추가했다. 프론트가 `shippingFee` 와
`freeShippingOver` 로 직접 계산하게 두면 **기준 금액을 무엇으로 볼지에서 갈린다** —
1차금만 세면 서버와 다른 숫자가 나오고, 화면에 "무료배송" 이라 떠 놓고 2차금에서
배송비가 붙는다. 기존 두 필드는 "3,000원 → 무료" 같은 표시를 위해 그대로 둔다.

## D-033. 셀러 주문 목록은 묶음 한 줄이고, 주문번호와 배송지를 /pay 에서 굳힌다

**계기:** 와이어프레임과 코드를 대조해 보니 셀러 어드민 네 화면(G1 · G6 · S10 · G10)에
API 가 하나도 없었다. 그중 G6 주문 목록을 먼저 만든 이유는 **나머지 셋이 전부 이 조회 위에
얹히기 때문**이다 — G1 의 "처리할 주문", S10 의 청구 대상 집계, G10 의 결제 내역이 모두
"셀러 기준으로 주문을 훑는다" 를 전제한다. 그때까지 주문 조회는 구매자의 `orderToken`
기준뿐이라 셀러가 자기 주문을 볼 길이 없었다.

### 한 줄은 묶음(order_group)이다

화면 카드는 상품 하나만 보여 주지만, **결제도 2차금도 배송비도 배송지도 일괄 청구도 전부
묶음 단위다.** 폼 단위로 쪼개면 한 번 결제한 장바구니 주문이 여러 줄이 되어 탭 건수와
S10 의 청구 대상이 어긋난다. 폼이 여럿이면 카드에서 "외 N건" 으로 접고 상세에서 편다.

조회 진입점도 `order_group` 이다. `order → sale_form → seller` 로 거슬러 올라갈 수도
있지만 그쪽은 인덱스가 없다. `order_group.seller_id` 에는 `idx_group_seller` 가 이미
있었고, 정렬까지 태우려고 `idx_group_seller_created (seller_id, created_at)` 를 더했다.

`CREATED` 와 `EXPIRED` 는 뺀다. **결제 전 체크아웃 세션은 주문이 아니다** — 15분 뒤
사라질 자리가 셀러 목록에 쌓이면 안 된다.

### 2차금 미납 탭은 "지금 청구할 수 있는 것" 만이다

`status in (PAID, SECOND_PENDING)` 에 **모든 활성 주문이 ARRIVED** 라는 조건을 더했다.
`isSecondPaymentDue()` 와 같은 판단이다. 입고 전 주문까지 넣으면 아직 청구할 수 없는 건이
청구 대상 숫자에 섞이고, 배송비가 묶음당 1회라 일부만 입고됐다고 청구하면 나눌 방법도 없다.

**발송 완료 탭은 당분간 항상 0건이다.** `SHIPPED` 로 올리는 코드가 없다 — 송장 등록이
7단계다. 화면이 다섯 칸이라 탭은 그대로 두고 0 을 내린다.

탭 배지 다섯 개는 `count(case when ... then 1 end)` 한 방으로 집계한다. `sum` 을 쓰지
않은 이유는 한 건도 없을 때 0 이 아니라 null 이 오기 때문이다.

### 주문번호 ORD-{yyMMdd}-{id}

여태 묶음을 가리키는 값은 `session_token(cs_xxx)` 과 `order_token(ord_xxx)` 뿐이었다.
둘 다 주소창에 실리는 임의 문자열이라 **셀러와 구매자가 전화로 주고받을 수 없고**,
화면의 검색창은 '주문번호' 로 찾게 되어 있다.

그날의 순번을 쓰지 않는다 — 순번을 매기려면 카운터 행을 잠가야 하고, 결제 시작 경로에
락을 하나 더 놓을 값이 아니다. `id` 가 이미 유일하므로 날짜와 붙이면 그대로 유일하다.

**재결제해도 번호가 바뀌지 않는다.** 실패해서 다시 결제한 것은 같은 주문이라, 번호가
갈리면 셀러와 구매자가 서로 다른 번호를 들고 이야기하게 된다.

### 배송지 스냅샷을 구현했다 — 그리고 /pay 가 배송지를 요구한다

`shipping` 테이블은 V1 부터 있었는데 **자바 엔티티도 복사 로직도 없었다.** 그래서
드로어의 수령인·연락처를 채우려면 `buyer_address` 마스터를 볼 수밖에 없었는데, 그건
"주문 당시 주소" 가 아니라 "현재 주소" 다. 구매자가 이사하면 이미 발송된 주문의
"어디로 보냈는가" 까지 같이 바뀌어 분쟁 때 근거가 없다.

복사 시점은 `order_token` · `order_no` 와 같은 `/pay` 다. `CREATED` 세션은 15분 뒤
사라지는 임시 자리라 배송지를 굳힐 이유가 없고, 셋을 한 지점에 모으면 **"주문이 성립한
순간" 의 정의가 하나로 남는다.** 재결제로 다시 들어와도 덮어쓰지 않는다.

**동작이 하나 바뀐다 — 배송지가 없으면 `/pay` 가 400 이다** (`SHIPPING_ADDRESS_REQUIRED`).
지금까지는 배송지 없이도 결제가 끝났는데, 그러면 셀러가 받은 주문에 보낼 곳이 없다.
point3 세션을 만들기 **전에** 막는다 — 스냅샷을 찍는 자리에서 처음 알면 이미 만든 세션이
버려진다. 결제까지 가는 기존 테스트 6개는 픽스처에서 배송지를 만들어 흡수했다.

### 연락처는 서버에서 가리고, 배송지 본문은 내보내지 않는다

드로어에는 `010-****-1234` 만 간다. 원본을 내려주고 프론트가 가리면 **응답 본문에는 그대로
남아 개발자도구로 보인다** (CLAUDE.md 규칙 10 과 같은 취지). 화면의 그 칸이 '배송지(잠금)'
이기도 해서 주소 본문은 아예 담지 않는다 — 목록을 훑는 내내 주소가 나갈 이유가 없다.

`CAPTURE_PENDING` 은 "확인 중" 으로 적는다. 실패로 찍으면 셀러가 구매자에게 재결제를
요구하고, 실제로는 출금된 건이면 이중 결제가 된다 (D-006).

### 남의 것은 없는 것과 똑같이 404

남의 `saleFormId` 로 거르면 `SALE_FORM_NOT_FOUND`, 남의 주문번호를 찍으면
`ORDER_GROUP_NOT_FOUND` 다. 403 이면 "그 id 에 뭔가 있긴 하다" 가 새어 나가
id 를 훑어 남의 판매를 알아낼 수 있다 (D-021 · D-029 와 같은 판단).

## D-035. 2차금 청구는 알림을 다시 내는 것이고, 취소된 폼의 잔금은 청구하지 않는다

**계기:** 와이어프레임 S10(2차금 일괄 청구)을 만들려고 보니 `SECOND_PAYMENT_DUE` 를
적재하는 곳이 **입고 처리 한 군데뿐**이었다. 알림을 놓치거나 구매자가 방치하면 셀러에게
재촉할 수단이 없다. `PaymentWriter` 의 "미수로 남겨 두고 재청구한다" 는 주석이 전제하는
그 재청구 경로가 없었다.

### 청구 = 알림 재발송 + 이력. 주문 상태는 건드리지 않는다

`docs/domain.md` 의 원안은 "S10 = `order_group.status` 를 `SECOND_PENDING` 으로 올리고
Outbox 적재" 였다. **그대로 하면 정작 결제가 막힌다.**

`isSecondPaymentDue()` 는 `status == PAID` 를 요구한다. 청구하면서 상태를 올리면 그 순간
false 가 되고, 구매자가 결제를 시작할 때 `prepareSecond` 가 `SECOND_PAYMENT_NOT_DUE` 로
튕긴다. 게다가 `SECOND_PENDING` 은 **구매자가 결제창까지 들어갔다**는 뜻으로 이미 쓰이고
있어서(`attachSession` 에서만 올린다), 셀러의 독촉과 뜻이 겹치지 않는다.

그래서 청구는 **알림 한 건을 다시 적재하고 이력을 한 행 남기는 것**으로 끝낸다.
출금이 아니다 — 자동출금이 없어 실제 결제는 구매자가 링크로 들어와 승인해야 한다.

`second_charge` 테이블을 새로 둔 이유는 상태를 안 바꾸기 때문이다. "청구했다" 는 사실이
`order_group` 어디에도 남지 않아서, 쿨다운 판정과 화면의 "마지막 청구일" 을 걸 자리가 없다.

**유니크 제약을 두지 않는다.** 미납이 이어지면 다시 청구하는 것이 정상이라 묶음당 여러
행이 쌓인다. `amount` 는 청구 시점 스냅샷이다 — 나중에 폼이 취소되면 청구액이 줄어드는데,
그때 "얼마로 청구했었나" 를 되짚을 수 있어야 한다.

### 쿨다운 24시간

같은 묶음을 24시간 안에 다시 청구하면 건너뛴다. **알림톡은 건당 발송 단가가 있고**
(와이어프레임 I 비고), 구매자에게 하루에 여러 번 독촉이 가면 차단당한다. 셀러가 버튼을
연타해도 하루 한 번을 넘지 않는다.

### 대상 집합은 G6 의 '2차금 미납' 탭을 그대로 쓴다

따로 짜면 화면의 탭 숫자와 실제 청구 대상이 어긋난다 — D-033 이 경고한 지점이다.
`findSellerOrders` 를 `tab=SECOND_UNPAID` 로 부르고 페이지를 나누지 않는다. 청구는 대상
전부에 나가야 하고, 50건씩 끊으면 셀러가 버튼을 몇 번 눌러야 하는지 알 수 없다.

금액 합계는 조회한 묶음들의 `secondPaymentAmount()` 를 자바에서 더한다. 집계 쿼리를 따로
짜면 같은 조건을 두 벌 관리하게 되고, 그게 정확히 위에서 피하려던 것이다.

### 같이 고친 것 — 부분 취소된 묶음은 잔금을 영영 못 받고 있었다

`isSecondPaymentDue()` 가 `orders` **전체**에 `allMatch(isArrived)` 를 요구했다.
폼 하나가 취소되면 그 주문은 영원히 `CANCELED` 라 조건이 **영영 참이 되지 않는다** —
부분 취소된 묶음은 남은 상품의 잔금을 받을 방법이 없었다.

게다가 `deposit2Total` 은 주문을 담을 때 누적된 스냅샷이라 취소돼도 줄지 않는다.
그대로 쓰면 **이미 환불한 상품의 잔금까지 청구**한다.

- `isSecondPaymentDue()` 를 `activeOrders()` 기준으로 바꿨다.
- `secondPaymentAmount()` 를 살아 있는 주문의 `deposit2Sum` 합 + 배송비로 바꿨다.
- **배송비는 굳힌 값을 그대로 쓴다.** 취소로 총액이 줄었다고 무료배송이 풀려 배송비가
  되살아나면 안 된다 (D-032 가 "주문 시점에 굳는다" 로 정했다).
- `firstPaymentAmount()` 는 건드리지 않았다. 이미 결제·환불이 끝난 금액이다.

**쿼리 쪽에도 같은 구멍이 있었다.** G6 의 `SECOND_UNPAID` 조건이 "취소·만료를 빼고 입고
안 된 것이 없다" 만 봐서 **전부 취소된 묶음도 통과**했다. 받을 잔금이 없는데 미납 탭에
잡히고 청구 대상에 섞인다. `exists (... status = ARRIVED)` 를 더해
`!alive.isEmpty()` 와 같은 조건으로 맞췄다.

### 지금은 알림이 실제로 나가지 않는다

발송기가 `LoggingNotificationSender` 라 로그만 찍고 SENT 로 넘긴다. 알림톡 계정·템플릿
심사가 끝나기 전까지 구매자에게는 아무것도 가지 않는다. 그래도 지금 만드는 이유는 청구
대상 집계와 이력이 생기고, 발송기를 갈아 끼우는 순간 그대로 동작하기 때문이다.

### 미결

- **도서산간·제주 추가 배송비** — S10 화면에 문구가 있는데 코드·문서 어디에도 그런 개념이
  없다. 추가 배송비 정책이 정해지지 않아 넣지 않았다.
- **배송지 변경 시 금액 충돌** — 와이어프레임이 스스로 "미확정" 이라고 적어 둔 항목이다.
  배송지를 바꿔 배송비가 달라지는 경우를 아직 다루지 않는다.

## D-036. 취소는 결제 상태를 바꾸지 않는다 — 상태 조회가 따로 알려준다

**계기:** 100원 실결제 검증(2026-09-09)에서 결제→취소를 한 바퀴 돌린 뒤,
셀러 주문 목록은 `취소됨`으로 보는데 **구매자용 `GET /orders/{orderToken}` 은
`PAID` 를 그대로 돌려줬다.** 그 응답으로는 취소 화면(B8-C)을 그릴 수 없다.

**원인은 버그가 아니라 표현의 공백이다.** `readStatus` 가 `payment.status` 만 보는데,
취소해도 결제 자체는 실제로 일어났으므로 `CAPTURED` 로 남는 것이 맞다. 환불은 그
뒤에 붙은 별개의 사실이고, 그걸 실어 보낼 자리가 응답에 없었다.

### 상태값을 늘리지 않고 필드를 얹는다

`Status` 에 `CANCELED` 를 더하는 방법도 있었지만 **부분 취소를 표현할 수 없다.**
폼 하나만 취소한 주문은 "취소됨"도 "결제 완료"도 아니다 — 남은 상품은 그대로 온다.

```
canceled        묶음 전체가 취소됐는가
refundedAmount  이 차수에서 지금까지 환불된 금액
```

부분 취소는 `canceled=false` 인데 `refundedAmount` 만 올라간다. 프론트는 이 조합으로
"일부 취소" 를 그릴 수 있다. `status` 는 결제가 실제로 일어났는지만 말한다.

전액 취소면 안내 문구도 바꾼다. "결제가 완료되었습니다" 를 그대로 두면 취소한
구매자가 결제가 살아 있다고 읽는다.

**승인 직후 응답(confirm)에는 얹지 않는다.** 그 시점에 환불이 있을 수 없다.

### 찾은 것 — `payment.refunded_amount` 는 죽은 컬럼이다

처음에 그 필드를 읽었더니 취소 뒤에도 0 이었다. 확인해 보니 **생성 시 0 으로 넣고
그 뒤로 아무도 갱신하지 않는다.** V1 스키마에 `ck_payment_refunded` CHECK 까지 걸려
있어서 유지되는 값처럼 보이지만 아니다.

실제 기준은 `COMPLETED` 인 `refund` 행들의 합(`RefundRepository.sumCompleted`)이고,
세금 안분도 그걸 쓴다. 상태 조회도 같은 것을 쓰게 했다. **컬럼을 지우거나 채우거나
둘 중 하나를 해야 한다 — 지금은 읽는 사람을 잘못 이끈다.**

## D-037. 같은 선택으로 다시 부르면 홀드를 새로 잡지 않고 이어받는다

**계기:** D-015 가 "비로그인 상태에서는 홀드를 잡지 않는다" 로 정하면서, 로그인 왕복에서
돌아온 프론트가 선택을 복원해 `POST /checkout-sessions` 를 **자동으로** 부르게 됐다.
그때 "진행 중인 세션이 있으면 이어받는다" 도 같이 정해 놓고 **코드에는 넣지 않았다.**
자동 호출이 두 번 들어오면(뒤로 가기 · 새로고침 · 리액트 이중 실행) 같은 구매자가
같은 상품의 재고를 두 벌 잠근다. 선착순 공동구매에서는 그만큼 남이 못 산다.

**결정:** `place` 는 새로 잡기 전에 이어받을 수 있는지 먼저 본다.

- **`CREATED` 만 본다.** `PAY_PENDING` 부터는 결제창까지 간 것이라 손대면 결제 중인
  주문을 건드린다.
- **항목이 정확히 같아야 한다.** 옵션별 수량을 통째로 비교한다. 다르면 이어받지 않는다 —
  사용자가 방금 고른 것과 다른 것을 결제하게 할 수는 없다. 그때는 새 세션이 생기고
  이전 홀드는 15분 뒤 만료 배치가 걷어 간다. 그 사이 재고가 이중으로 묶이는 것은
  지금 받아들이는 비용이다.
- **홀드가 살아 있어야 한다.** 만료 배치가 아직 안 돌았을 뿐인 세션을 돌려주면 구매자는
  남은 시간 0인 화면을 받고 결제 단계에서 홀드 검증에 튕긴다. 그럴 바에는 새로 잡는다.
- **셀러로 좁히지 않는다.** 부르는 쪽이 아직 셀러를 모른다 — 셀러는 옵션에서 역산된다
  (`OrderCreator`). 어차피 항목이 똑같은지 대조하므로 같은 항목이면 셀러도 같다.

**`CheckoutResumer` 를 별도 빈으로 뺀 이유는 트랜잭션 경계다.** `OrderService.place` 는
`@Retryable` 이 트랜잭션 **바깥**에 있어야 해서 일부러 `@Transactional` 이 없다
(D-002 에서 정한 것). 같은 클래스 안에 두면 자기 호출이라 프록시를 타지 않고,
지연 로딩된 주문 항목을 읽는 순간 터진다. `OrderCreator` 를 나눈 것과 같은 이유다.

**이어받기는 새로 잡기 전에 판정한다.** 뒤에 두면 이미 홀드를 잡은 뒤라 의미가 없다.
`OrderCreator.create` 는 `REQUIRES_NEW` 라 그대로 두면 되고, 읽기 전용 판정만
앞에 붙였다.

**남은 것:** 항목이 달라진 경우 이전 홀드를 즉시 풀어 주면 이중 점유가 사라진다.
안 한 이유는 "다른 탭에서 다른 것을 담는 중" 과 구분할 방법이 없어서다 —
잘못 풀면 살아 있는 장바구니를 남이 가져간다. 15분이 짧아 지금은 두고 본다.

## D-038. 셀러 홈은 요청 하나로 주고, 숫자는 주문 목록에서 빌려 온다

**계기:** 와이어프레임 G1(셀러 홈)이 한 화면에서 세 가지를 요구한다 — 처리할 주문
건수(2차금 미납 · 발송 대기, DUE-110), 진행 중 판매 카드(모집 68/100 과 D-5),
최근 주문. 이걸 한 번에 주는 API 가 없었다.

**결정 1 — 엔드포인트 하나(`GET /seller/home`).** 셋을 따로 부르게 두면 홈을 열 때마다
왕복이 셋이고, **셋의 시점이 어긋난다.** 배지에는 2건이 남았는데 목록에는 이미 처리된
것이 보이는 순간이 생긴다. 화면 하나가 요청 하나다.

**결정 2 — 세는 일을 새로 만들지 않는다.** 처리할 주문은 G6 의 탭 배지 집계
(`countSellerOrderTabs`)를 그대로 쓰고, 최근 주문은 G6 목록의 첫 장이다.
홈이 자기 방식으로 세면 목록과 숫자가 갈라진다. **그 숫자는 S10 청구 대상 수라
갈라지면 돈 문제가 된다** (D-035). 테스트가 두 값이 같은지 직접 대조한다.

카드도 `SellerOrderPageResponse.itemOf` 를 재사용한다 — 프론트가 홈과 목록에서 같은
컴포넌트를 쓰게 하려는 것이다. 모양이 갈라지면 "외 N건" 이나 결제 문구 규칙을
두 군데서 따로 손보게 된다.

**결정 3 — 일시중지도 진행 중 판매다.** `SELLING` 과 `PAUSED` 를 같이 싣는다.
일시중지는 끝난 판매가 아니라 셀러가 손을 대야 하는 판매다 — 목록에서 빼면
멈춰 둔 것을 잊는다. 상태를 실어 보내 배지로 구분하게 한다.

**결정 4 — 마감 임박순.** D-day 가 이 카드의 존재 이유다. 마감일이 없는 단독 판매는
뒤로 보낸다. MySQL 은 NULL 을 가장 작게 보므로 `ORDER BY (closes_at IS NULL), closes_at`
로 밀어 낸다 — JPQL 에 NULLS LAST 가 없어 네이티브로 썼다.

**결정 5 — D-day 는 날짜로 센다.** 시간 차로 나누면 오늘 밤 11시 마감이 D-0 이 아니라
D-1 로 보인다. 화면의 D-5 는 달력 상의 날 수다.

**결정 6 — 모집 숫자는 주인에게 늘 보인다.** 구매자용 `ProductAvailabilityResponse` 는
`progressPublic` 이 꺼져 있으면 감추지만, 그건 **남에게** 감추는 설정이지 주인에게
감추는 것이 아니다. 자기 판매의 모집 현황을 자기가 못 보면 홈이 쓸모없다.

**범위 밖 — G10 결제 내역은 만들지 않았다.** 와이어프레임에는 셀러가 카드에서 바로
취소·환불 접수를 하는 화면이 있는데, 셀러가 남의 결제를 취소할 실질적 필요가 지금은
없다. 공구가 깨지는 경우는 `ShortfallCancelBatch` 가 자동으로 처리하고(D-026),
나머지 취소는 구매자가 자기 화면에서 한다. 열어 두면 **셀러 계정이 곧 환불 권한**이
되는데, 돌려준 돈은 되돌릴 수 없다 — 감사 로그·권한 분리를 같이 만들어야 하는 일이다.

정말 비어 있는 자리는 따로 있다. **셀러가 자기 사정으로 판매를 접는 경우**(재료 수급
실패·발주 불가)다. 지금은 수동 마감만 되고 이미 결제된 주문은 그대로 남는다.
그건 건별 즉시취소가 아니라 "판매 취소" 한 번에 그 폼 전체를 되돌리는 동작이어야 맞고,
미달 취소 경로를 그대로 재사용하면 된다 — 방아쇠만 배치에서 셀러 버튼으로 바뀐다.

## D-039. 운영자 인증을 앱에 붙이지 않는다 — 심사는 사람이 하고 접근은 프록시가 막는다

**계기:** 현황판에 `운영자 인증` 이 오래 `점검 필요` 로 남아 있었다. `/admin/*` 에 앱
차원의 인증이 없어서, 프록시의 404 가 유일한 방어선인데 스웨거에 그 API 의 존재가
드러나 있다는 지적이었다.

**결정: 앱에 운영자 로그인·권한 체계를 만들지 않는다.** 셀러 가입이 오면 기획측이
사람 눈으로 확인하고 허가하는 방식으로 정했다(팀 결정, 2026-09-10). 그러면 필요한 것은
**신청자 목록과 수락 두 가지뿐**이고, 로그인·역할·감사 로그를 갖춘 관리자 시스템은
지금 만들 이유가 없다.

접근 제어는 그대로 프록시가 맡는다 — `deploy/Caddyfile` 의 `@admin` 블록이 `/admin/*`
전체를 404 로 막는다. **앱은 자기가 열려 있다고 가정하고, 밖에서 못 들어오게 하는 일은
한 겹 앞에서 한다.**

### 만든 것

- `GET /admin/sellers` — 신청자 목록. **먼저 낸 신청이 위에 온다.** 심사는 대기열이라
  최신순으로 두면 늦게 낸 신청만 처리되고 오래된 것이 바닥에 깔린다.
- `POST /admin/sellers/{sellerId}/approve` — 수락 (이미 있던 것)

**사업자번호는 이 목록에만 담는다.** `SellerResponse` 는 "사업자번호·정산계좌를 담지
않는다" 를 규칙으로 삼는데, 그건 셀러 본인과 구매자가 보는 응답이라 담을 이유가 없어서다.
반면 **심사는 사업자번호를 확인하는 일 그 자체**라, 그 값이 없으면 이 API 로는 승인
여부를 판단할 수 없다.

**정산계좌는 여기에도 담지 않는다.** 심사에 필요한 값이 아니다 — 돈을 보낼 때 쓰는
값이고 그 시점은 한참 뒤다. 필요한 것만 꺼낸다.

### 남은 것 — 기획측이 이 API 를 어떻게 부를지

지금은 `/admin/*` 이 프록시에서 404 라 **인스턴스 안에서만 호출된다.** SSM 으로 접속해
`curl` 을 치는 방식인데, 엔지니어가 아닌 사람에게는 쓸 수 없는 경로다.

밖에서 부를 수 있게 하려면 Caddy 를 손봐야 한다. 스웨거와 같은 방식 —
`basic_auth` 를 걸고 계정 해시를 Parameter Store 에 두는 것 — 이 가장 적은 변경이다.
**스웨거와 계정을 공유하지는 않는다.** 그쪽은 프론트 개발자 전체가 쓰는 계정이고,
이쪽은 셀러를 승인하는 권한이다.

그 변경은 이번에 하지 않았다. 기획측이 실제로 어떤 화면·경로로 심사할지가 정해지면
그때 맞춰 여는 것이 맞고, 그 전에 열어 두면 **인증 없는 승인 API 가 인터넷에 노출된
시간만 늘어난다.**

## D-040. 알림톡은 SOLAPI 에 직접 붙이고, 승인된 템플릿만 내보낸다

**계기:** 카카오 알림톡 `1차금 결제 완료` 템플릿이 승인됐다(2026-09-10). 발송 경로는
SOLAPI 로 정해졌고 `pfId` 와 템플릿 id 를 받았다. `LoggingNotificationSender` 를
실제 발송기로 바꿀 차례다.

### 공식 SDK 를 쓰지 않는다

이유가 셋이다.

1. SDK 가 **코틀린 + kotlinx.serialization** 이라 Java 17 프로젝트에 런타임을 통째로 들인다
2. 예외를 자기 방식으로 감싸서 **4xx 와 5xx 를 나누기 어렵다** (CLAUDE.md 규칙 2)
3. base URL 이 고정이라 **WireMock 으로 실패를 재현하기 어렵다**

실제로 필요한 것은 HMAC 헤더 한 줄과 POST 하나뿐이다. `Point3Client` 와 같은 모양으로
붙였고, 서명 방식은 공식 SDK 의 `Authenticator` 를 그대로 따랐다 —
`hex(HMAC-SHA256(apiSecret, date + salt))`, salt 는 하이픈 뺀 UUID, date 는 ISO-8601.
테스트가 그 서명을 같은 방식으로 다시 계산해 맞는지 본다. **틀리면 배포한 뒤에야
401 로 알게 되는 종류의 실수다.**

### 200 이 성공이 아니다

`send-many/detail` 은 HTTP 200 을 주면서 본문의 `failedMessageList` 에 건별 실패를 담아
온다. 상태 코드만 보면 **한 건도 안 나갔는데 outbox 가 SENT 로 넘어간다.** 2차금 청구가
그렇게 사라지면 구매자는 잔금을 낼 줄 모르고 셀러는 이유를 알 수 없다. point3 에서
"브라우저의 성공 신호는 성공이 아니다" 와 같은 판단이다.

단건인데 `send-many/detail` 을 쓰는 것도 이 때문이다 — **건별 실패를 돌려주는 유일한
엔드포인트**라서 어느 건이 왜 실패했는지 로그에 남길 수 있다.

**건별 실패는 4xx/5xx 로 가르지 않고 전부 재시도 대상으로 둔다.** SOLAPI 상태 코드는
수십 종이고 그중 무엇이 영구 실패인지 문서만으로 단정할 수 없다. 잘못 영구 실패로
판정하면 청구가 조용히 사라진다. 8회 재시도 뒤 DEAD 로 남기면 사람이 보고 판단한다 (D-027).

### 승인된 템플릿이 없는 이벤트는 조용히 넘어간다

지금 적재되는 이벤트는 넷인데 승인된 템플릿은 하나뿐이다. 나머지를 그냥 보내면
4xx 로 떨어져 **8회 재시도 끝에 DEAD 로 쌓이고, "아직 승인 전" 이 장애처럼 보인다.**
그래서 템플릿 id 가 설정에 없으면 예전처럼 로그만 남기고 SENT 로 넘긴다.

**템플릿 id 를 설정에 채우는 순간 그 이벤트가 나가기 시작한다 — 코드는 손대지 않는다.**

### payload 를 넓히지 않고 조회로 채운다

템플릿 변수는 다섯이다(`userName` · `goodsName` · `prepayment` · `billTime` · `LINK`).
적재 지점이 넷이라(결제·입고·2차금·환불) payload 에 넣으려면 템플릿이 늘 때마다 넷을 다
고쳐야 하고, **이미 쌓인 PENDING 행은 옛 payload 라 새 변수를 못 채운다.** 조회로 채우면
적재 쪽은 그대로 두고 `AlimtalkMessageFactory` 만 바뀐다.

발송기와 조립부를 나눈 것은 트랜잭션 경계 때문이다 — 조립은 DB 를 읽고(짧은 트랜잭션),
발송은 외부를 부른다(트랜잭션 밖, 규칙 1).

**금액만은 payload 에서 읽는다.** 그때 청구한 값이라서다 — 부분 취소 뒤 다시 계산하면
알림 문구가 실제 결제 금액과 달라진다. 결제일시도 같은 이유로 outbox 행의 `created_at`
을 쓴다. 재시도로 며칠 뒤 나가도 문구는 그때 그 시각이어야 한다.

`goodsName` 은 `OrderGroup.representativeTitle()` 로 옮겨 **셀러 주문 목록(G6)과 같은
문구**를 쓰게 했다. 갈라지면 구매자가 받은 알림과 셀러가 보는 목록의 제목이 다르다.

### ⚠ 남은 것 — 수신번호가 구매자 본인 번호가 아니다

**구매자 본인 전화번호가 DB 에 없다.** `buyer` 에는 `kakaoId` · `nickname` · `payerId`
뿐이고, 카카오 로그인에서도 닉네임만 받는다. 있는 번호는 `buyer_address.phone` 과
그 주문 시점 스냅샷인 `shipping.phone` 인데 **둘 다 수령인 번호**다.

지금은 그 번호로 보낸다. **선물 주문이면 결제 완료 알림이 받는 사람에게 간다** —
불편을 넘어 구매 사실이 제3자에게 새는 문제다. 호칭(`userName`)도 수신번호에 맞춰
수령인 이름을 쓰도록 맞춰 두었지만, 근본 해결은 아니다.

**그래서 `NOTIFY_PROVIDER` 기본값을 `log` 로 두었다.** 운영에서 파라미터를 바꾸기 전까지
아무것도 나가지 않는다. 켜기 전에 셋 중 하나를 정해야 한다.

- 카카오 로그인 동의항목에 전화번호를 추가한다 (검수 필요, 기존 가입자는 재동의)
- 결제 단계에서 "알림 받을 번호" 를 따로 받는다 (프론트 수정 필요)
- 배송지 번호를 그대로 쓰기로 하고 그 사실을 화면에 알린다

D-020 에서 카카오 토큰을 세션에서 빼며 *"알림톡에 필요해지면 그때 별도로 보관한다"* 고
적어 두었다. 그때가 지금이다.
