# 프로젝트 규칙
**모든 응답은 한국어로 한다.** 코드 주석과 커밋 메시지도 한국어.
셀러가 판매 링크를 발급하고 구매자가 그 링크로 들어와 결제하는 공동구매 · 단독판매 플랫폼.
결제는 point3 PG를 연동한다.

## 기술 스택

- Java 17 / Spring Boot 3.x
- MySQL 8.0 / Spring Data JPA
- Flyway (스키마 마이그레이션)
- 단일 애플리케이션 (모놀리식). MSA로 쪼개지 않는다

## 절대 어기지 말 것

결제 도메인의 규칙이다. 어기면 돈을 잃거나 초과 판매가 발생한다.

1. **외부 API 호출을 `@Transactional` 안에 두지 않는다.**
   point3 응답이 30초 걸리면 DB 락을 30초 잡는다.

2. **4xx와 5xx를 같은 catch로 잡지 않는다.**
   4xx는 확정 실패(되돌려도 안전), 5xx·타임아웃은 결과 불명(되돌리면 미수금).
   `RestClientException` 하나로 잡으면 안 된다.

3. **결과가 불확실하면 아무것도 되돌리지 않는다.**
   타임아웃·5xx·네트워크 오류에서는 `CAPTURE_PENDING`을 유지하고 홀드도 풀지 않는다.
   대사 배치가 확정할 때까지 기다린다.

4. **승인 API를 호출하기 전에 `CAPTURE_PENDING`을 커밋한다.**
   이 기록이 없으면 서버가 죽었을 때 승인 여부를 추적할 방법이 없다.

5. **금액은 항상 DB 값을 쓴다.**
   프론트가 보낸 금액, successUrl 쿼리의 `amount`는 검증 기준으로 쓰지 않는다.

6. **브라우저가 보낸 성공 신호를 결제 성공으로 취급하지 않는다.**
   `successUrl` 도달, `POINT3_CAPTURE_READY` 수신은 "승인을 요청해도 된다"는 신호일 뿐이다.
   성공 판정은 서버가 받은 승인 API 응답의 `status: captured`로만 한다.

7. **`captured`를 확인하기 전에 상품을 지급하지 않는다.**

8. **재처리 가능한 지점에는 반드시 멱등 가드를 둔다.**
   배치가 같은 건을 다시 처리해도 재고가 두 번 차감되면 안 된다.

9. **홀드 만료 배치는 `CAPTURE_PENDING`인 묶음을 건너뛴다.**
   승인 결과를 모르는 상태에서 재고를 남에게 넘기면 초과 판매가 된다.

10. **로그에 토큰 · PIN · 전체 `payer_id`를 남기지 않는다.**

## 코딩 규칙

- 재고 확보는 `SELECT` 후 `UPDATE`가 아니라 **조건부 `UPDATE` 한 방**으로. 영향 행 0이면 품절
- 여러 행을 잠글 때는 항상 **id 오름차순 정렬** 후 잠근다 (데드락 방지)
- 데드락 · 락 타임아웃은 `@Retryable`로 2~3회 자동 재시도. 단 `OutOfStockException`은 재시도하지 않는다
- 배치는 `FOR UPDATE SKIP LOCKED`로 인스턴스 간 분산
- 시간은 전부 `Instant` 또는 `LocalDateTime` + 명시적 타임존. `Date` 금지
- 금액은 `int` / `long`. `double`, `float` 금지

## 작업 방식

- 한 번에 한 단계씩. `docs/roadmap.md`의 순서를 따른다
- 동시성과 실패 처리 코드에는 반드시 테스트를 함께 작성한다
- point3 연동 테스트는 WireMock으로 타임아웃 · 5xx · `processing` 응답을 재현한다
- 스키마 변경은 Flyway 마이그레이션 파일로. 기존 파일을 수정하지 않는다
