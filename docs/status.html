도메인별 개발 현황

docs/roadmap.md 의 체크박스가 아니라 실제 코드·스키마·배포 상태를 읽어 정리했다. 이번 갱신부터는 와이어프레임(바이올렛페이4팀_와프 Main) 의 화면 명세와도 대조했다 — 맨 아래 행이 화면 ID 와 API 를 맞춰 본 결과다. 도메인 이름을 누르면 항목별 상태가 펼쳐진다.

09-09, 운영에서 100원이 실제로 결제되고 취소됐다. 연동키 수령 → 세션 발급 → 승인 captured → 전액 환불까지 한 바퀴다. 샌드박스가 없어 미뤄 두었던 검증이라, 이걸로 결제·취소 도메인의 마지막 물음표가 지워졌다. 운영 IP 등록은 정말 필요 없었다. 검증 중에 두 가지가 드러나 같이 고쳤다 — point3 키가 컨테이너까지 전달되지 않던 것, 그리고 취소한 주문이 상태 조회에서 계속 결제 완료로 보이던 것(D-036). 셀러 어드민은 G1 홈까지 붙어 한 바퀴가 돌아간다 — 홈에서 처리할 주문을 보고(G1), 목록에서 고르고(G6), 잔금을 청구한다(S10). 세 화면이 같은 집계를 쓴다 (D-038). G10 결제 내역은 만들지 않기로 했다 — 셀러가 남의 결제를 취소할 실질적 필요가 없고, 열면 셀러 계정이 곧 환불 권한이 된다. 남은 것은 프론트 SDK 연동, 알림톡 계정·템플릿 심사(항목 9종 중 5종 미구현), 그리고 송장 등록이다.
완료 부분 진행 점검 필요 진행 전
다음 한 걸음 — ① 프론트 SDK 연동. API 는 준비됐다(point3-api 6절). 함정 셋만 넘기면 된다 — orderId 자리에 sessionId, setAmount 는 1 고정, 그리고 successUrl 도달만으로는 결제가 끝나지 않는다(confirm 을 불러야 한다) → ② 알림톡 수신번호 정하기 — 결제완료 템플릿은 붙였는데(D-040) 구매자 본인 번호가 DB 에 없어 켜지 못하고 있다. 지금 켜면 선물 주문의 결제 알림이 수령인에게 간다 → ③ 송장 등록 — 알림톡 3번(발송 완료)이 이걸 기다리고, G6 의 발송 완료 탭이 항상 0건인 이유도 이것이다
